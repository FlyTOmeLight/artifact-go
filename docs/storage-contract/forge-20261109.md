# Forge / JuiceFS 合同验收（2026-11-09）

本轮在 OrbStack `forge` namespace 的现有 release 上运行真实 S3 契约探针；除将 Forge Web 升级到 revision 11 以启用 `connect-src` 和 `configRevision` 外，没有修改存储参数、PVC 或业务 bucket。目标是确认客户端直传、STS 精确授权、跨租户隔离和凭证期限在当前 JuiceFS 1.4.1 网关上是否成立。

## 环境与入口

| 项 | 值 |
| --- | --- |
| 集群 | OrbStack，namespace `forge`，release `forge` |
| 对象存储 | JuiceFS 1.4.1 多 bucket gateway（`forge-juicefs`） |
| 探针入口 | 合同探针 `http://127.0.0.1:19010` 转发到 `forge-juicefs:9000`；浏览器验收转发到 `forge-artifact:19010`（nginx 代理同一 gateway） |
| 服务身份 | `s3-user`（root，负责 bucket 管理与清理） |
| 签发身份 | `sts-user`（普通 issuer，负责 `AssumeRole`） |
| 测试 bucket | `tenant-t-000000000000000000000001`、`tenant-t-000000000000000000000002` |
| 探针 | `scripts/verify_s3_contract.py --checksum-mode declared` |
| Web 入口 | `http://127.0.0.1:8483`，release `forge` revision 11 |
| Web CSP | `connect-src 'self' http://127.0.0.1:19010` |

测试 bucket 使用 `tenant-t-<24 hex>` 命名，与真实租户 bucket 规则一致。Forge chart 的 `storage-iam` init container 会给 issuer 绑定只覆盖 `arn:aws:s3:::tenant-t-*/*` 的策略；使用 `artifact-contract-probe-*` 这类命名会被正确拒绝，不能据此判断部署故障。

本轮登录验收还续签了 `tenant-lab` 的 CA/服务端证书，并清除了浏览器中指向旧账号的 `forge_identity` cookie。两者是本机登录环境的修复，不改变对象存储契约。

## IAM 身份与租户隔离

- 每个 Forge 部署只有一个普通 IAM issuer（seed 中的 `sts-user`），不按租户或用户创建 IAM 用户。`storage-iam` init container 给它绑定一条 canned policy，资源为 `arn:aws:s3:::tenant-t-*/*`，动作为 `s3:GetObject`、`s3:PutObject`、`s3:ListMultipartUploadParts`、`s3:AbortMultipartUpload`。
- 租户隔离在每次签发时完成：Artifact 服务先校验调用方的身份、租户和项目，再用该 issuer 调用 `AssumeRole`，session policy 精确到本次对象 key 和所需动作。临时凭证的有效权限是 issuer 基础策略与 session policy 的交集。
- JuiceFS 忽略 `RoleArn`，直接认证 issuer 本身。这里的 `AssumeRole` 不是 AWS 的跨账户角色，不能据此推断存在按租户的角色；`tenant-t-<tenantID>` 的边界由服务端鉴权和 session policy 共同保证。
- 因此 issuer 的长期密钥是部署级凭据，必须只给 Artifact 服务；泄露后可以签发覆盖任意 `tenant-t-*` 的会话。session policy 只缩小单次授权，不替代服务端鉴权。

## 结果

实际执行并通过的检查：

- `grant_deadline`：STS 返回的 `Expiration` 不超过请求截止时间。
- `single_upload`：精确 key 的 `PutObject` 成功。
- `single_trusted_checksum`：按当前契约核对对象大小；摘要为客户端声明。
- `other_key_denied`、`object_delete_denied`、`bucket_policy_read_denied`：临时凭证不能越 key、删除完整对象或读取 bucket policy。
- `stream_read`、`stream_early_close`：读取流可读且可提前关闭。
- `multipart_part_1/2`、`list_parts`、`multipart_complete`、`multipart_abort`、`multipart_abort_preserves_object`：分片上传、列举、完成、中止可用。
- `tenant_buckets_positive_control`：两个测试 bucket 都能被服务身份写入。
- `other_tenant_bucket_denied`：本租户临时凭证不能写另一个租户 bucket。
- `delete_missing_idempotent`、`cleanup_object_absent`：重复删除不存在对象成功，清理后 HEAD 返回 404。
- `credential_expiration`：带 `--wait-expiry` 实测等待 900 秒超期；超期后再次发起 `PutObject` 被底层网关明确拒绝（JuiceFS 淘汰会话后返回 `InvalidAccessKeyId`，`request_rejected: true`），无越期写入风险。
- `browser_cors`：真实 Chromium 从 `http://127.0.0.1:8484` 的干净测试页发起签名 `PUT`、`GET`、`HEAD`、`Range GET`，四项全部通过；网关对 `http://127.0.0.1:8483` 的 `OPTIONS` 预检也返回 200 并回显 origin、方法和签名头。
- `browser_web_origin_direct_upload`：Forge Web 升级到 revision 11 后，在 `http://127.0.0.1:8483` 的同源文档 `/runtime-config.json` 中发起签名 `PUT`、`GET`、`HEAD`、`Range GET`，四项全部通过；响应头确认 `connect-src 'self' http://127.0.0.1:19010`。未登录访问 `/` 会在 401 后跳转，因此验收页使用同源无跳转文档，不改变 CSP 作用域。
- `browser_ui_authenticated_upload`：在真实 Chromium 登录态完成完整闭环。使用部署引导操作员登录并进入租户 `t_767d0159113adcf8bffedcb9` 的项目 `p_6a54419083fafae1df96c90f` 后：
  1. `POST /storage/v1/storage/files` 预登记返回 200，状态为 `uploading`；
  2. `POST /storage/v1/storage/grants`（`preset: upload`）取得 STS 临时凭证，bucket 为 `tenant-t-767d0159113adcf8bffedcb9`；
  3. 浏览器 SigV4 `PUT` 直传 `http://127.0.0.1:19010` 返回 200；
  4. 用同一上传凭证执行 `GET` 返回 403 `AccessDenied`，确认只允许上传动作；
  5. `POST /storage/v1/storage/files/complete` 返回 200，状态变为 `ready`，`size: 45`；
  6. `POST /storage/v1/storage/grants`（`preset: download`）取得读凭证，签名 `GET` 返回 200 且内容一致，`HEAD` 返回 200，`Range GET` 返回 206 且 `bytes 6-18` 正确；
  7. `DELETE /storage/v1/storage/files/{fileID}` 返回 202，状态变为 `deleting`，进入异步清理。
- `adapter_context_cancellation`：Go Adapter 的 `EnsureBucket`、`CreateGrant`、`CheckBucket`、`Stat`、`Delete`、`HasIncompleteUploads` 在父 context 取消后返回的错误保留 `context.Canceled`，且不泄漏 endpoint 或凭据。Adapter 没有 `Open`/`io.ReadCloser` 契约，字节读取由客户端用 STS 直连，因此“阻塞读取退出”和 reader 关闭不属于当前接口。
- `worker_expiry_multipart_recovery`：文件以 2 秒 TTL 注册并创建未完成 multipart 后，storage worker 扫描到期文件、调度删除任务并在真实 JuiceFS 上中止该 key 的分片上传；PostgreSQL 与 MySQL 均通过。

按后端能力记为 pending 的检查：

- `versioning_configuration`、`lifecycle_configuration`、`cors_configuration`：JuiceFS 1.4.1 对 bucket versioning/lifecycle API 返回 `NotImplemented`，对 bucket CORS 返回 `NoSuchCORSConfiguration`。
- `other_tenant_versioning_disabled`：同上，无法通过 S3 API 查询。
- `multipart_lifecycle_execution`：没有配置后端 lifecycle，无法观察到期自动回收。
- `bucket_policy_modification`：探针只读，不修改远端策略。
- `stream_cancellation`：不适用。Go Adapter 没有流式读取接口，客户端直接读取 S3 字节；Adapter 的取消行为已由 `adapter_context_cancellation` 覆盖。

`invalid_checksum_denied` 在 `declared` 模式下记为 `not_applicable`：当前契约只保存客户端声明，不要求后端拒绝错误摘要。

## 结论

1. **STS 链路成立**：`sts-user` 能签发临时凭证；session policy 精确到文件 key，跨 key 和跨 bucket 写入均返回 `AccessDenied`。root 不能 `AssumeRole`，符合 JuiceFS 行为，不能据此判断网关不支持 STS。
2. **chart 的 issuer 策略有效**：`storage-iam` init container 绑定的策略覆盖 `tenant-t-*/*`，真实租户命名 bucket 的直传可用。此前用非租户命名测试 bucket 得到的 403 是策略正确拒绝，不是部署缺陷。
3. **JuiceFS 1.4.1 不实现 bucket versioning/lifecycle/CORS API**：不能把这些 API 的 `NotImplemented` 当作业务失败；需要分别确认替代机制。
4. **网关 CORS、Forge Web CSP 与浏览器路径可用**：对 `Origin: http://127.0.0.1:8483` 的 `OPTIONS` 返回 200；真实 Chromium 从干净页面和 Forge Web 同源文档都完成了签名 `PUT/GET/HEAD/Range`。登录后的真实 UI 路径也已完成预登记→STS 上传→`PUT`→Complete→下载/`HEAD`/`Range`→删除的完整闭环，上传凭证越权读取返回 403。
5. **未完成分片回收依赖业务 worker**：storage worker 在文件过期或删除时会按精确 key 列举并中止分片上传；不能把 S3 lifecycle 配置存在当作该能力的唯一证据。
6. **摘要按声明处理**：JuiceFS 不回显或不校验 SHA256；当前契约只核对对象存在和大小，发布后对象内容由客户端负责。
7. **前端 CSP 阻塞已关闭**：`forge-tenant-web` 新增 `csp.connectSrc`，只接受 HTTP(S) origin；OrbStack release 已升级到 revision 11，运行中的 Pod 确认放行 `http://127.0.0.1:19010`。后续更换存储 origin 时必须同步修改 `web.csp.connectSrc` 并递增 `web.configRevision`，否则旧 Pod 不会重载 nginx。
