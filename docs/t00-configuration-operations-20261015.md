# T00 开发配置与失败任务恢复建议

日期：2026-10-15。状态：用户已批准全部建议；对应业务配置与行为按实施切片落地。本文件给 OrbStack 开发验收使用，不作为生产容量承诺。内部 HTTP/JSON 已由用户确认；其余数值均为已确认的开发默认值。

## 开发配置

| 配置 | 确认值 | 依据及约束 |
| --- | --- | --- |
| MaxFileBytes | 1 GiB（1073741824 字节） | 可测试大文件和分片；现有 JuiceFS 逻辑容量9 GiB，单文件上限不保证多文件总量可装下。生产训练模型需要另定容量，不沿用此上限 |
| MaxFilesPerVersion / 每份草稿清单上限 | 1000 | 与公开单批上限一致；并不保证1000个文件可合成一份STS，实测JuiceFS session policy最多2048字符，应按最终序列化policy检查；超限返回GrantScopeTooLarge，客户端拆grant批次 |
| 文件准备 TTL | 24小时 | 给断网续传、跨日草稿编辑与失败另存留窗口；从登记时固定，续授权、确认和失败重试不重置 |
| upload STS 默认及最大期限 | 1小时 / 1小时 | 后端最短900秒，固定截止与签发耗时需要余量；长文件续发继续同一multipart，仍受原准备ExpiresAt约束；写授权及失败签发预留可能使回收多等近1小时 |
| download STS 默认及最大期限 | 1小时 / 1小时 | ready还受准备期限约束，bound不受历史准备期限约束；读取不延缓回收 |
| ReferenceChange attempt期限 | 120秒，不续期 | 文件字节已提前上传，期限仅覆盖元数据查询、绑定及最终本地提交；以artifact数据库时间判定；迟到进程必须在最终事务检查失败 |
| 内部HTTP连接 / 单次请求超时 | 1秒 / 5秒 | 超时不代表未提交；相同ReferenceID重放，或查询结果；不能据此直接释放已提交业务引用 |
| 内部HTTP批次 | 1–1000项；8 MiB请求体 | 与公共限制保持易理解的一致边界；跨批不保证原子，完整计划必须先持久化 |
| 两域worker并发 | 每域每副本2个 | 本地资源下先以低并发验证，多副本共享数据库领取；两域分别限流 |
| worker租约 / 续租 | 60秒 / 15秒 | 使用数据库时间及领取token；执行外部调用有截止时间，失租后不能写完成结果 |
| 扫描周期 | 5秒 | 包括到期文件、到期attempt和可领取任务；扫描不代表精确时刻删除 |
| 重试退避 | 指数退避，1秒起，最多60秒，加抖动 | 保留服务端Retry-After约束；不在数据库锁内sleep |
| 自动失败预算 | 每轮最多20次实际失败 | 达到预算写failed并告警，载荷与义务保留；等待NotBefore或等待删除回执不算执行失败，总执行次数单独统计，不作为失败预算；只有可确认执行错误增加失败次数，失租/崩溃后接管不猜测失败原因，持续失租由监控告警 |
| 每域DB连接池 | MaxOpen=10，MaxIdle=5 | combined仍每域各一组；生产总连接量按副本数计算，不在T00凭空确定生产池大小 |
| 未完成分片检查 | 每小时扫描；24小时以上候选 | storage用服务身份扫描和中止，不能给客户端ListBucket权限。只有关联文件已deleting/deleted且写授权已过期才中止；未知key只报告，不盲删 |

固定业务限制继续是payload 256 KiB、annotations 64 KiB、总请求体8 MiB、公开登记/确认/grant每批1–1000。上述1000文件上限是**完整清单**上限，不可通过多批绕过。S3字节不经过8 MiB业务请求体。

分片年龄不是删除活跃上传的依据。正常文件回收在等待LastGrantExpiresAt后枚举该文件精确key的UploadId并逐一Abort，再Delete对象和复查迟到写入；小时扫描补漏不能替代该路径。准备TTL届满停止新授权，已绑定引用不会因原TTL过期消失。不存在后端生命周期配置时，不能把配置了“24小时”当作自动清理已实现。

实际STS拒绝短于15分钟的凭证。若请求ttlSeconds或文件剩余准备时间扣除签发预算后不足15分钟，在签发前返回HTTP400 GrantTTLTooShort，不签发超过文件截止的凭证；已同步公开契约，T08实现。不通过把有效期向上取整绕过准备期限。签发预算5秒：锁内固定绝对截止D，发出STS前取floor(D−当前时间−5秒)；不足900秒拒绝，返回时仍须校验当前时间<Expiration≤D，不能只改响应时间伪装裁剪。LastGrantExpiresAt签发前预留max(old,D)，不减去预算，失败也不缩短。显式请求900秒在此模型下通常无法满足，客户端应使用默认期限或更大有效期限。

当时的独立存储环境（现已退役）启动参数包含`--trash-days 1`。当前部署参数以 [Forge umbrella chart](../charts/forge/README.md) 为准。DeleteObject成功和HEAD 404证明S3入口不可读，不能证明底层SSD空间立即释放。建议保留当前trash配置，在运行说明明确该区别；若开发磁盘压力要求立即释放，再单独评估调整trash策略。文件回收任务按既定S3删除回执收尾，不新增等待磁盘块GC的业务状态。

## failed任务如何人工恢复

T04实现一个仅部署维护者可用的命令入口，artifact和storage分别连接自己的数据库，不增加公共task API。T00只定义其行为，不写操作现有数据库的脚本，因为任务表尚不存在。

命令输入包括域、TaskID、expectedRevision（或等价CAS版本）、操作人、原因、工单/记录号。先dry-run显示Kind、终态、失败摘要、不可变载荷指纹、当前attempt/租约及受影响数量；不输出凭证或大业务JSON。操作人确认的执行使用同一数据库事务：

1. 锁任务，要求仍为failed、版本未变、没有有效租约；running、succeeded和已重排任务拒绝。
2. 保留TaskID、Kind、业务attemptID/交接ID、完整载荷及原NotBefore；不得重新生成ReferenceID、修改业务终态或缩短失败文件保留窗口。
3. 开始新一轮有界执行预算；保留累计执行次数、上一轮失败及原因记录，增加恢复次数；NextRunAt=max(now,原NotBefore)，旧领取token失效。
4. 同事务持久保存操作人、原因、时间和前后状态的审计记录；审计写失败则不重排。在现有两域任务行分别增加RunGeneration、TotalAttempts和RecoveryEvents JSON字段，RecoveryEvents追加每次恢复的小型记录，不复制业务载荷、不新增第15张表；不能只写非事务日志后声称可靠。

重新排队不等于任务完成；后续仍调用幂等Release/查询/Abort/Delete并取得回执。重复恢复命令通过CAS拒绝，不重复清零预算。针对“引用已不存在”“后端404”等具体状态沿用对应处理规则，不人工篡改成succeeded。

验收：双进程同时重排最多一方成功；旧worker token不能完成；事务断开后查主库恢复记录；failed期间义务不丢；重排后仍遵守NotBefore和当前引用状态。这些运行结果需T04/T07/T09实际实现后取得，T00没有把文档演算算成数据库测试通过。

## 本次校验与尚缺证据

已按现有设计核对：期限不重置准备窗口；只读grant不阻止回收；attempt截止与worker租约互不替代；各域数据库独立；任务预算耗尽不丢义务；公开接口数量仍27。1 GiB小于9 GiB逻辑容量，1000项与公开批次一致，但该算术检查不代表容量/性能压测。

实际后端能力和期限约束以[T00 JuiceFS报告](storage-contract/t00-juicefs-report.md)为准。业务计时、双库竞争、恢复审计、SDK续传及1000文件压力均尚未实现，分别归T04、T07–T10、T12验证。生产的容量、租户配额、并发和保留时长需要部署方输入；本次不把本地建议自动推广到生产。
