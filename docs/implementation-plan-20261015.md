## 各任务的验收边界

### T00：把风险转成证据与小契约

产出接入清单、内部交接消息约定、开发配置和新版存储报告。探针不再以实际摘要或防覆盖作为发布条件，保留旧报告历史事实。使用普通 IAM 身份验证合法操作正例后再验证拒绝范围，实测到期及清理；凭证不写入文档或日志。遗留分片清理需要实际运行证据，等待期间可推进其他任务。

T00 分项记录通过/待接入/不满足，不作为一个阻塞所有开发的大开关。工作副本基线先确定；后端权限问题只阻塞依赖它的文件验收。若实际环境无法满足契约，提交明确差异和处理选项，不擅自修改已定业务边界。

### T01：先交付可运行的集合服务

落点：cmd/server、service、app/artifact、scope、集合 table、artifactv1、tests/fixture 与检查入口。集合四路由走真实 HTTP/SDK，PG/MySQL 均验证 Type/scope 唯一性、NULL 项目、历史读取及归档；服务可启动和正确退出。框架正式依赖、工具链与生成器在此锁定，不用本地 replace。

从此每个切片都更新 SDK、Controller/OpenAPI 和检查入口；无需等待全部业务完成才建立 CI。不要求 T01 创建 storage 数据库或 S3 凭据；模块装配与资源所有权遵循独立部署边界。

### T02：版本编号与成功去重先可信

落点：version 发布/编号/指纹、Version/CreateRequest、版本 SDK。两个独立进程不能重复编号；响应丢失同键重试返回原身份，异参409；失败不推进编号。测试数字词法、字段缺失与 null、JSON 字节边界及版本墓碑身份规则所需数据约束。

本切片只证明纯 JSON 基础路径。带文件、alias、retention、草稿来源依赖后续任务，不以忽略这些输入或临时兼容实现冒充完整 CreateVersion。尚未实现的组合行为不宣称可发布使用。

### T03：所有 alias 变更遵守同一规则

落点：alias/mutation、版本注释及保护、对应 HTTP/SDK。直接操作、发布和将来的淘汰共用名称、Revision、目标归属/ready 与墓碑规则；latest 只读。发布携带保护与 alias 的事务回滚行为在真实双库验证。

### T04：先完成本地业务回收与持久任务基础

落点：retention.Plan、version/deletion、BackgroundTask、artifact worker。预览无副作用；发布和定时淘汰均遵守保护、最小保留和 alias 条件；纯 JSON 删除清内容而保留身份。多进程验证领取、租约、续租、旧 token、失败预算和受控重排。

worker 是现有任务的具体执行器，不抽成通用工作流框架。文件释放载荷与外部交接由 T09 接入，不能先放一个调用 storage 的共享事务快捷实现。

### T05：纯 JSON 草稿也采用最终保存契约

落点：draft、Draft/DraftFile、DraftCreateRequest、保存回执需要的 ReferenceChange、草稿 SDK。两页同 Revision 编辑一胜一冲突；GET 不返回混合快照。首次就支持保存 requestKey、appliedRevision 和当前 draft 的区分；空引用计划同样幂等，不先实现无回执 PUT。

创建响应丢失、修改后重放、硬删后410、归档/历史 scope、来源版本复制、指定修订发布均验收。Web 行为用两个 SDK 客户端验证服务契约，Web 编辑器不在本仓库交付范围。

### T06–T08：storage 先能独立使用

T06 验证固定名称与可信管理入口；普通用户不能借用户 Header 创建空间。T07 的请求/200响应均顶层数组，逐项错误与整请求错误分开；直接通过测试存储身份写入对象来验收确认，明确这不等于用户直传已完成。未引用文件过期、显式删除、重试、迟到对象与 failed 预算由 storage 自身负责。

T08 才完整交付客户端直传链：grants 保留对象结构，按精确 key 和 S3 Actions 签发，未过期 ready 可读，bound 读取与引用在 T09/T10 回归。真实 JuiceFS 验证普通 PUT、multipart、读写权限反例、跨 key/桶、实际期限；读取不延长准备期或等待只读凭证回收。控制型 adapter 负责故障测试，不能替代真实协议验收。

### T09：先做一个可恢复的单文件发布闭环

落点：storage/binding、可信传输适配、version/references、ReferenceChange、backgroundtask/references 与不可变任务载荷。先通过单文件直接 CreateVersion 把交接接入真实业务入口，再覆盖引用内部故障，不先造独立无调用方的流程引擎。

顺序固定为持久计划 → storage 独立 Bind → artifact 本地提交与释放任务 → 后台 Release。验收丢响应、先 Release 后 Bind、多批部分成功、commit/abort 竞争、旧 attempt、未知提交、失败补偿原 ExpiresAt 和稳定释放墓碑。恢复 worker 只中止/清理；从第一天就不跨域传 tx。独立进程和数据库的交接验收在此开始，不留到 T12 才首次尝试拆分。

### T10：把完整引用语义应用到草稿与所有文件场景

落点：draft/references、版本完整清单、发布/淘汰/删除的释放任务与收尾。覆盖单文件无草稿、单文件有草稿、多文件、文件夹四流程，以及复制、替换、改路径、移除重加、同 scope 跨 Artifact 复用。

必须验证最后引用才回收、非最后释放稳定完成、CAS 失败附件在原准备窗口可另存、成功版本不丢引用、逻辑删除后投递延迟仍可读的边界。草稿204仅代表删除和释放义务持久；带文件版本收尾等待所需回执。显式大 JSON 作为普通文件走同一路径，不自动转存或回填 payload。

### T11：补齐统一持久引用入口

URI 编解码可随前序版本响应按需实现；本任务交付完整 Resolve 路由。实际读取校验 scope/type 和资源可见性，alias 返回真实固定版本，文件只返回清单元数据。Resolve 不签发权限、不调用 S3、不建立保留引用；客户端使用已完成的 storage grants 读取。

### T12：证明整套系统可以交付

按 Spec Testing Decisions 逐项回归。两种数据库各运行相同业务和并发用例，交接含两个独立服务进程和两个独立数据库；验证 artifact-only、storage-only、combined 装配和退出。与真实身份接入核对历史 scope、归属删除、新操作拒绝及成功请求重放。

使用实际 SDK/HTTP/浏览器到 S3 路径验收，完成 failed 任务受控恢复、引用积压观测和备份恢复演练。备份恢复须检查两域决策与引用一致性，不能仅恢复单库后假定交接仍正确。交付 Docker/配置/运行说明和生成物一致性；不自动生产部署、发布版本或创建 GitHub Release。
