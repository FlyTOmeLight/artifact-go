# 当前实现的跨模块 Review

日期：2026-10-15。范围：当前完整工作树（无提交基线，包含全部未跟踪源码）、当前系统 [Spec #1](https://github.com/FlyTOmeLight/artifact-go/issues/1)、技术设计、代码结构设计与引用交接协议。不提交或推送代码。

## 审查结论

确认一类遗漏：Spec 实现决策43及技术设计运行观测条款要求的业务指标没有完整实现。原有框架请求日志、SQL日志和手工查询不能替代发布冲突、锁查询耗时、保留阻塞、任务积压和回收失败指标。已补齐，定向验证与完整回归均通过。

对以下跨模块链路未发现新的业务缺陷：

- 草稿/版本的精确作用域、并发Revision、失败指纹和成功回放，以及先Bind再提交的持久决策。
- 文件复用、移除后重加、完整释放计划、Release先于Bind墓碑、最后引用等待物理回执。
- 发布、编号、alias和retention的本地原子性；Resolve的一致快照和可见性。
- grants的精确权限、写授权保守上界、事务外签发后二次核验；storage与artifact不共享事务或查询对方表。
- SDK逐请求身份、错误链，以及独立/组合装配、HTTP排空和后台资源所有权。

ConsumerID 采用既定的永久稳定服务身份，凭据轮换不改变身份。发布和释放通过同一稳定消费者执行；引用与墓碑在storage侧按ConsumerID隔离，不增加业务owner回调。

## 修正内容

`internal/telemetry`复用server-go当前依赖的Prometheus库和默认registry，不另建监控服务。新增请求结果、锁查询耗时、文件逐项结果、已持久记录的任务失败、各域任务快照、最老到期等待、保留阻塞及已知墓碑位置的探测结果。

指标只使用固定路由、状态、operation、任务kind等有限维度。资源ID写关联日志，不作指标标签；不读取或记录Header、请求正文和STS。批量登记/确认的HTTP200仍可包含逐项失败，单独统计这些结果，保持原数组响应契约。

两个worker各自查询本域表，每次采集有2秒预算。指标注册或采集失败不停止回收、不修改失败预算，也不把查询失败报成零积压。停止worker先阻止新采集，再等待已开始的数据库读取退出，避免另一个服务并发抓取指标时提前关闭数据库。

`service.SetupHTTP`仅按`HTTPServer.MetricsEnable`安装框架`/metrics`，默认关闭；不启用其他管理或调试中间件。入口由运维网络保护，不增加业务SDK接口。运行方式、信号含义、重复数据库快照的聚合规则和初始告警建议见[部署说明](../deploy/artifact/README.md)。

锁指标包括SQL往返和实际等待，不声称是纯数据库锁阻塞时间。客户端到S3的字节上传没有经过服务，其网络和分片失败由客户端/S3监控；墓碑探测只检查已知deleted位置，不枚举未知对象。
